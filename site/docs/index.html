Sanity + a visual editor for Astro · open source

Okapi

Okapi adds two things to an Astro project, new or existing: Sanity as the database, and a visual editor of its own where your team and your clients build and edit pages on top of the real design.

Your coding agent installs it, whichever one you use, by following a guide in the repo. This view explains how to ask for it and how to work with it afterwards.

  • Astro 7.3 · static
  • Sanity 6.3.0 · pinned
  • React 19
  • Tailwind 4 on tokens
≈1 KBof JS on a page without blocks that need it
91 KBof JS (gzip) on a page with a slider or a 3D logo
0 KBof editor code on the public site, checked on every build
2paths: a new project or an existing Astro project

Product

What it is

It isn't a site template. Okapi is the content and editing layer you add to an Astro project. Your project stays yours: your pages, your design and your deployment. Okapi adds:

Sanity as the database

Login, roles, drafts, history, images and CDN. We don't maintain any of it. The Studio lives at /studio on your site.

Okapi Editor

Our visual editor at /studio#/editor. You type directly on the page, drag blocks, style with your tokens and build components.

Pages built in the editor

The routes you choose are built in the editor and served as static HTML. Only sections with a slider or a 3D logo load JavaScript.

Team and client

What each person can do depends on their Sanity role and is decided per project in src/okapi.policy.ts. This is the default; the agency changes it. Admins can preview the editor as any role with View as.

Can…TeamClient
Edit text, rich text, links and imagesYesYes
Reorder blocks within the designYesYes
Insert, duplicate and delete blocksYesNo
Style panel (spacing, color, radius, breakpoints)YesNo
Create, edit and detach componentsYesNo
Use the AI chat (if the project has it on)YesDepends on role
PublishYesDepends on role

With editor, the client publishes on their own. With contributor, they leave drafts and someone on the team publishes. The roles available depend on your Sanity plan.

With your agent

Add it to your project

The installation is written up in the repo's INSTALL.md, designed so any coding agent can follow it: Claude Code, Codex, Cursor or another. Open your agent in the project folder and ask.

Any agent

The agentDetects whether the project is new or existing, asks you whatever is missing, copies what it needs without overwriting your files, configures Sanity and runs verify.
You checkThat your pages are unchanged, that /studio opens and that the editor shows the page.

Claude Code, with the skill installed

Add Okapi to this project.
The agentThe okapi-astro skill brings the same INSTALL.md and follows it.
You checkThe same things. Install the skill once, from the repo, with cp -R skills/okapi-astro ~/.claude/skills/.

New or existing project

  • Empty folder: the agent starts from the Okapi repo, which is already an Astro project with example blocks that you replace later.
  • Existing project: the agent adds Okapi to your project. Your pages, layout and configuration stay as they are. Editor pages are served on routes that don't exist yet, or wherever you tell it.

What it will ask you

  • Which Sanity organization the project goes in, or the project ID if you've already created one.
  • For an existing project: which routes come from the editor, and whether the home page comes from the editor or stays yours.
  • Which modules you want: slider, 3D logo, reusable components and the AI chat. What you don't pick isn't installed.
  • Who will edit: only your team, a client who publishes, or also someone who only leaves drafts.
  • Whether to load example content to see the editor working right away.

Before changing anything, it shows you the plan (which blocks go, which dependencies are removed, which roles stay) and waits for your OK. The chat and components can be switched on or off later in src/okapi.config.json.

What you do yourself

Anything that needs your account. The agent gives you the exact command or steps:

  • Log in to Sanity and, if you want, import the example page.
  • Invite the client.
  • On your host: environment variables (including the AI key, if you use the chat), the domain in CORS and the publish webhook.
  • The logged-in editor test (Before you hand off).
Never paste tokens or passwords into the chat

The guide is written so that no agent needs them. If an agent asks for one, don't give it: tell it to follow INSTALL.md.

With your agent

How to ask

The split that keeps the work organized:

Done in the editorAsked of your agent
Text, links and imagesNew blocks, or making something that already exists editable
Adding, reordering and duplicating sections and blocksHow a block looks
A block's style, within the tokensThe token values (your design)
Building and reusing componentsRoutes, layout, header and footer of the editor pages
PublishingConnecting publishing to deployment
  • Token names don't change. Their values do. The style panel relies on those names.
  • The editor only sees registered blocks. For something to be editable, it has to be a block.
  • Okapi doesn't animate. If your project already uses GSAP, Motion or CSS animations, it keeps them: animation lives in your code, not in the editor.
  • Ask it to verify. "Run verify" before calling anything done.
  • Publishing is going live. With the webhook set up, every publish rebuilds the site within minutes. The agent never publishes without your explicit yes.
  • The chat can only do what your role can. Its changes are drafts and undo in one step. It never publishes.
  • Okapi gets fixed in its own repo. src/core is the same in every project: if something in the editor breaks, the fix goes to the repo and is then pulled into each project.
  • Don't ask it to upgrade Sanity along the way. It's pinned to 6.3.0 on purpose.

Why an iframe

The canvas lives on its own route (/edit-canvas), separate from the Studio:

  • Isolated CSS: the site's CSS doesn't mix with the Studio's.
  • Real breakpoints: desktop, tablet and mobile change the iframe's width.
  • No exposed drafts: the route is public but has no data of its own. It only draws what an already authenticated editor sends it, over same-origin postMessage.

Block paths

Every block carries data-sanity-path on its root, holding its GROQ path inside the document, for example:

sections[_key=="a1f3"].content[_key=="9c2e"].items[_key=="77d0"]

That path ties together the click on the canvas, the selected layer, the properties panel and the write to Sanity. Structural operations (core/editor/ops.ts) are pure functions over those paths, validated against the block registry. The undo history is a stack of document snapshots.

Product

The public site

Pages are static (output: "static"). If the AI chat is on and the host runs functions (Vercel, Netlify, Cloudflare Pages), Astro adds one server function, /api/editor-chat; everything else is still prerendered. With the chat off there is no adapter at all. At build time, each page requests its document from Sanity, and loadSite() fetches settings, navigation, the route map and the component library. Build reads bypass Sanity's CDN on purpose, and a production build stops if Sanity can't be reached or the env is missing, so a failed fetch never deploys an empty site.

HTML first, JavaScript only where needed

PageBuilder renders on the server. Every top-level section that contains a block with js in the registry is wrapped as an island:

<!-- display: contents → doesn't affect the layout -->
<div data-island='{"section":{…},"ctx":{…},"components":{…}}'>
  <section class="section" data-theme="dark">…already-rendered HTML…</section>
</div>

Base.astro includes a minimal script. If the page has at least one island, it imports core/render/hydrate.tsx, which runs hydrateRoot on each island with the same props. If there are none, the page doesn't load React.

npm run verify checks this on every build: no public HTML references editor or Studio code, and the home page doesn't exceed 250 KB of JS.

SEO included

  • Titles and description: every page has metaTitle, metaDescription, ogImage and noindex. When they're empty, they fall back to the values in Settings, and if those are empty too, to the defaults in code.
  • Generated tags: absolute canonical, og:*, Twitter card, sitemap.xml, robots.txt and JSON-LD Organization on the home page.
  • URLs: all of them come from pageHref() and resolveLink(). Internal links are references to pages, not hand-typed paths. Adding languages later means changing those two functions.

Product

Okapi Editor

It's the Studio's first tab. It has three columns: pages and layers, canvas and properties. Along the top are undo and redo, + Add, the device selector and Publish. The right column has two tabs, Properties and ✦ Chat. Both side columns resize by dragging their edge (double-click resets).

What you can do

  • In-place text. Double-click headings, paragraphs, eyebrows, buttons, and card titles and bodies. Rich text has a floating toolbar with bold, italic, link and unlink.
  • Layers. A tree with drag and drop (before, after or inside), insert, duplicate, delete, move, and copy and paste between pages.
  • Dragging on the canvas. The selected block shows a ⠿ handle. A blue line shows where it will land, and the move is validated with the same rules as the layers.
  • Multi-select. ⇧ or ⌘ + click on the canvas or in the layers. Delete, duplicate, copy and move apply to all of them.
  • Images. Drag a file onto an image, card or section background, or upload it from the panel.
  • Properties generated from the schema. Every field of every block has its own control; verify fails if any field is left without one.
  • ✦ Chat. Ask for changes in your own words and attach up to 3 images. Only what your role allows; changes are drafts that undo in one step. See Permissions and AI chat.

Saving and publishing

Everything you do is saved automatically as a draft. Nobody sees it until you press Publish. After publishing, the site updates on the next build: a couple of minutes if the project has the webhook set up.

How it saves

The editor uses the Studio's own document store, with no additional SDK. Changes apply locally right away and are saved as a draft. Publish publishes the document. Since the site is static, publishing triggers a rebuild (see Hosting and publishing).

Text editing without caret jumps

While you type, the canvas holds back the renders coming from the editor. When you finish, it restores the exact DOM React expects, and only then applies the new value. Rich text is converted between Portable Text and editable HTML in core/editor/richtext.ts, which keeps the targets of existing links by their key.

Product

Styles and tokens

All of the design comes from src/theme/tokens.css, the first file you change in every project. It holds the colors per theme (light, dark, brand), the radii, the type scale, spacing and page width. Tailwind 4 exposes them as utilities (bg-surface text-fg gap-md rounded-main), and since colors read the section's data-theme, every block adapts to the theme on its own. Tailwind's default palette is removed on purpose: a new color is added as a token.

Style panel

Every block has a design field that the editor shows as the style panel. It offers tokens only, no free-form CSS, and each value can be set for all screens, tablet and mobile.

PropertyValues
Margin, paddingnone xs sm md lg xl 2xl 3xl
Background, text colorbg surface surface-2 fg muted brand brand-contrast border

core/style/stylesheet.ts turns those values into a single stylesheet per page, with one selector per block. Panel values use !important because the panel has the final say over that block:

[data-b="9c2e"][data-b] { padding-top: var(--space-lg) !important; }
@media (max-width: 767px) {
  [data-b="9c2e"][data-b] { padding-top: var(--space-sm) !important; }
}

Box

The free-form container: it stacks, lays out in a row or builds a grid, with token gaps, alignment and wrapping. It can be nested. On tablet, grids drop to 2 columns and on mobile to 1; rows stack on mobile.

Product

Components

A component is a component document that holds sections. A page uses it through a componentRef block (an instance). If you edit the component, all of its instances change.

In the editor

  • Make component: saves the selected section to the library and replaces it with an instance.
  • + Add: lists the library's components so you can insert them as instances.
  • Edit component: opens the original component for editing.
  • Detach: turns the instance into a standalone, editable copy.
  • The canvas selects an instance as a single block.

Per-instance overrides

If you double-click a text or drop an image inside an instance, the change is saved on that instance only, in its overrides list. The original is untouched. Each override targets "<blockKey>.<field>", is applied at render time (core/render/overrides.ts), and the panel lists them with a Reset button.

Current limitation

Components are whole sections and only live at the top level of a page. They can't be nested or inserted inside another section. See What's next.

Product

Permissions and AI chat

Each project decides who can do what in src/okapi.policy.ts: every Sanity role gets a list of permissions and, optionally, the block types it may add. The editor and the chat follow it. The chat can never do more than the person using it.

PermissionAllows
textEdit texts, rich text and links
imagesReplace images
styleThe style panel (tokens only)
settingsBlock settings: variants, sizes, layout
reorderMove blocks up and down
structureAdd, duplicate and delete blocks (limited by blocks)
componentsMake, detach and insert library components
publishPublish
chatUse the AI chat
The policy shapes the editor; it isn't a lock

The real boundary is the Sanity role: what the API lets that person write. Someone technical can write anything their role allows without going through the editor. Give clients the narrowest Sanity role that works.

How the chat works

  • The editor sends the request, with the person's Sanity session, to the site's own function /api/editor-chat.
  • The function checks the session with Sanity, works out the person's permissions, reads the page from Sanity and asks the model with the project's key, stored in the host. The key never reaches the browser.
  • The model only proposes changes. The editor checks each one against the permissions, the block registry and the schema, and applies the valid ones as one undo step, saved as a draft. The chat never publishes.
  • Images: attach up to 3 (📎, paste or drop). The original is uploaded to Sanity; the model sees a smaller copy.
  • Model picker: every provider with a key on the host appears (Anthropic, OpenAI, OpenRouter). AI_MODELS limits the list; the first is the default.

Cost and privacy

  • One key per project, with its own spend limit at the provider. Every request has a token cap and a per-person rate limit; the drafts-only role has no chat by default.
  • The page being edited and any attached images are sent to the chosen provider. Say so to the client.
  • The chat is optional: with features.chat: false in src/okapi.config.json the site stays fully static.

Working with it

The code

The rule the product rests on: src/core is the same in every project. A fix in core is made in the Okapi repo and then pulled into each project. What's specific to each project lives in blocks, theme and its layouts. Once there are 3 or more projects in production, core becomes a private package and fixes arrive with npm update.

Rules most often broken

  • Blocks receive everything as props and carry {...editable(…)} on their root. They never fetch: the canvas draws them with the document it receives.
  • Style with Tailwind utilities built on the tokens. No literal colors.
  • Design assets (logos, textures) are code; they don't go in the CMS.
  • macOS is case-insensitive: never put Foo.tsx and foo.ts in the same folder.

Working with it

Adding a block

  1. Schema and component

    src/blocks/<type>/schema.ts with defineType and an icon from @sanity/icons, plus <Type>.tsx, which receives { block, path, ctx }.

  2. Registry

    An entry in meta.ts: title, slot if it contains other blocks, margin, and js if it runs anything in the browser.

  3. Maps

    Register it in schemas.ts and components.tsx. The compiler reports an error until you do.

  4. Editor (optional)

    Content on insert in defaults.ts, editable text in TEXT_TARGETS and image drop in IMAGE_FIELDS (both in CanvasApp.tsx).

// src/blocks/meta.ts
quote: { title: "Quote", margin: true },
ticker: { title: "Ticker", js: true },
gallery: { title: "Gallery", js: (b) => b.layout === "carousel" },
// src/blocks/quote/Quote.tsx
export function Quote({ block, path, ctx }: BlockProps<QuoteData>) {
  return (
    <blockquote className="text-h-lg text-fg"
      {...editable(ctx.documentId, ctx.documentType, path, block._type)}>
      {block.text}
    </blockquote>
  );
}

If the component already exists in your project, the path is the same: the component reads everything from block instead of props or hardcoded text, and if it was an .astro file it becomes .tsx.

To remove a block, delete its folder, its entry in meta.ts, the two map entries and any accepts that names it. The compiler takes you to each one.

The deploy hook URL is a secret: whoever has it can trigger builds. Keep it only in Sanity's webhook and the host.

Working with it

Quality and testing

npm run verify

Run it before every handoff and after any change to core. It checks the things that break silently:

  • The installed Sanity version has its patch.
  • Links and routes resolve correctly (routes.check).
  • Every field of every block has a control in the panel (check-editor-schema).
  • Insert, move, delete and duplicate keep the document valid, and island detection is correct (ops.check).
  • Tokens produce the expected CSS, with no selector injection (stylesheet.check).
  • Overrides apply to the right block and never touch the original (overrides.check).
  • Each role's permissions gate every change the chat proposes, and provider requests have the right shape (chat.check).
  • Rich text round-trips to editable HTML without breaking out of attributes (richtext.check).
  • The build passes, the public HTML contains no editor or Studio code, and the home page stays at or under 250 KB of JS.
  • The home page has real content, an absolute canonical, a sitemap and robots.txt.
  • Given a URL (npm run verify -- https://your-domain), it also checks that /, /studio and /edit-canvas respond.

Logged-in smoke test

Flows that need a login can't be automated without credentials. Test them by hand, on a throwaway page, before handing off a site:

  1. Type into a heading on the page, reload, and check that the text is still there.
  2. Bold, italic and a link in a paragraph. Insert, duplicate, delete and drag a layer. Undo and redo.
  3. Drop an image on an Image block: it uploads and shows up.
  4. Make component on a section. Edit text on an instance: only that one changes. Reset. Edit component: all of them change.
  5. Publish, then npm run build, and the change is on the static page.
  6. Log in as a client-role user: they don't see styles or structure actions.
  7. With View as each role, only what okapi.policy.ts allows shows up; the chat refuses the rest.
  8. ✦ Chat: "make the selected heading shorter" is applied, and Undo reverts it.

Context

Decisions

Why it's built this way. Before changing any of these, read the reasoning.

Our own editor instead of Sanity Presentation

Problem. Presentation was slow for editing: you had to click the overlay, find the field in a form and wait for the round trip. You couldn't type on the page, and it depended on 7 patches.

Decision. Replace only the editing UI, using public Studio APIs. Presentation, /preview, draft mode and visual-editing were removed.

Sanity as the database

Problem. Login, roles, drafts, history, real-time updates and images are months of infrastructure work.

Decision. Don't build any of that: Sanity handles it, and the Studio stays available for settings, menus and collections.

An iframe canvas with no data of its own

Problem. The site's CSS and the Studio's can't mix, and a canvas route with data would expose drafts.

Decision. A same-origin iframe that only draws what the authenticated editor sends it. It also gives real breakpoints.

A static site with per-section islands

Problem. Hydrating the whole page cost 138 KB of JS even when almost nothing moved.

Decision. Without Presentation, there's no need to hydrate everything: plain HTML, and React only in sections with js.

Sanity pinned to 6.3.0

Problem. patches/ adjusts Studio forms and only applies to an exact version.

Decision. Pin the version and make install and verify fail if it drifts. Upgrading is planned work.

Token-only styling

Problem. Free-form CSS and absolute positioning amount to building an entire page builder, and they break brand consistency.

Decision. The panel only offers tokens. New blocks are written in code, and the editor composes and styles with them.

Copied, not a package yet

Problem. A private package from day one adds versioning before you know what changes per project.

Decision. Install by copying, following a guide for agents, with src/core left intact. Turn it into a package once there are 3 or more sites in production.

Installation for any agent

Problem. The team doesn't use a single agent, and an installation tied to one goes stale in the others.

Decision. An INSTALL.md and an AGENTS.md in plain Markdown. The Claude Code skill just fetches them and follows them.

No i18n yet, but ready for it

Problem. No current project needs it.

Decision. Every URL goes through pageHref() and resolveLink(). Adding languages happens in one place.

No animation library

Problem. Shipping GSAP and animated blocks tied every project to one library and its licence terms for visual builders, and added weight.

Decision. Okapi doesn't animate. Projects that already animate keep their own tools. Page JS with islands went from 139 KB to 91 KB.

The AI chat runs on the site's server

Problem. A key in the browser can be read by any script in the Studio, and clients would see it.

Decision. One function per site, /api/editor-chat, with the project's key in the host. It verifies the Sanity session and the role before asking the model.

Ask before installing

Problem. Installing everything by default left projects with modules and dependencies nobody asked for.

Decision. The agent asks first and okapi:setup applies the answers the same way every time.

Glossary

Block
A piece of the page: a heading, paragraph, image, card, slider…
Section
A horizontal band of the page that holds blocks. It has a theme (light, dark or brand), spacing and a background.
Box
A free-form container for laying out blocks in a column, a row or a grid.
Component
A section saved to the library so it can be reused across pages.
Instance
Each use of a component on a page. If you change the component, every instance changes.
Override
A text or image changed on a single instance, without touching the component.
Token
A named design value: a color, a spacing step, a radius. Changing it changes the whole site.
Draft
What you've edited but haven't published yet. Only the team sees it.
Publish
Put content live. With the webhook, the site rebuilds within minutes.
Build
When the site is generated from the published content. It takes a few seconds, plus install time.
Webhook
The notification Sanity sends on publish so your host runs a build.
Studio
Sanity's admin panel, at /studio. The editor lives inside it.
Canvas
The view of the page inside the editor, where you click and type.
verify
The project's automated check: if it passes, the important parts work.
INSTALL.md
The guide any agent follows to add Okapi to a project.
AGENTS.md
The rules the agent reads before working on the project. Claude Code reads them through CLAUDE.md.
Skill
A Claude Code shortcut: okapi-astro fetches INSTALL.md and follows it.
Core
src/core, the editor's code. It's the same in every project and gets fixed in the Okapi repo.
okapi:setup
The install script: keeps only the modules you chose.
okapi.config.json
What the project uses: the chat and components, on or off.
okapi.policy.ts
Who can do what in the editor and the chat, per Sanity role.
✦ Chat
The editor's AI assistant. It proposes changes; you keep or undo them.
