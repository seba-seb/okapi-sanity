Starter + editor visual · uso interno

Remarkable

La base con la que arrancamos cada sitio de cliente: un sitio Astro estático y rápido, un editor visual propio para armar y editar páginas sobre el diseño real, y Sanity guardando el contenido.

  • Astro 7.3 · estático
  • Sanity 6.3.0 · fijo
  • React 19
  • Tailwind 4 sobre tokens
  • GSAP 3.15
≈1 KBde JS en una página sin bloques animados
138 KBde JS (gzip) en una página con motion
0 KBdel editor en el sitio público, controlado en cada build
≈4 sde build completo, Studio incluido

Producto

Qué es y para quién

Remarkable es un repo plantilla. Cada proyecto nuevo se copia de él y se personaliza en tokens, header, footer y bloques. La infraestructura (src/core) es la misma en todos los proyectos. Tiene tres partes:

Sitio público

Astro genera HTML estático en el build. Solo las secciones con animaciones o sliders cargan JavaScript. Funciona en cualquier hosting estático.

Remarkable Editor

Nuestro editor visual, como pestaña del Studio en /studio#/editor. Se edita texto sobre la página, se arrastran bloques, se estilan con tokens y se arman componentes.

Sanity

La base de datos. Login, roles, borradores, historial, imágenes y CDN. No lo mantenemos nosotros; el Studio queda para settings, menús y colecciones.

Equipo y cliente

El mismo editor muestra dos vistas según el rol en Sanity. El equipo (rol administrator) puede alternar a la vista de cliente para revisar lo que ve el cliente.

Puede…EquipoCliente

Reordenar bloques dentro de lo diseñadoSíSí
Insertar, duplicar y borrar bloquesSíNo

Crear, editar y separar componentesSíNo
PublicarSíSegún rol

Con editor el cliente publica solo. Con contributor deja borradores y publica alguien del equipo. Los roles disponibles dependen del plan de Sanity.

Por qué un iframe

El canvas vive en su propia ruta (/edit-canvas), igual que en Webflow:

  • CSS aislado: el CSS del sitio no se mezcla con el del Studio.
  • Breakpoints reales: desktop, tablet y mobile cambian el ancho del iframe.
  • Motion con la misma política que el sitio (ver Motion).
  • Sin borradores expuestos: la ruta es pública pero no tiene datos propios. Solo dibuja lo que le manda, por postMessage del mismo origen, un editor ya autenticado.

Rutas de un bloque

Cada bloque lleva en su raíz data-sanity-path con su ruta GROQ dentro del documento, por ejemplo:

sections[_key=="a1f3"].content[_key=="9c2e"].items[_key=="77d0"]

Esa ruta une el clic en el canvas, la capa seleccionada, el panel de propiedades y la escritura en Sanity. Las operaciones de estructura (core/editor/ops.ts) son funciones puras sobre esas rutas, validadas contra el registro de bloques. El historial de deshacer es una pila de snapshots del documento.

Producto

El sitio público

El sitio es 100% estático (output: "static", sin adapter). En el build, cada página pide su documento a Sanity y loadSite() trae settings, navegación, el mapa de rutas y la librería de componentes. Las lecturas del build salen sin la CDN de Sanity, a propósito: un rebuild disparado por una publicación podría leer una respuesta vieja de la caché.

HTML primero, JavaScript solo donde hace falta

El PageBuilder se renderiza en el servidor. Cada sección de primer nivel que contiene un bloque con js en el registro se envuelve como isla:

<!-- display: contents → no altera el layout -->
<div data-island='{"section":{…},"ctx":{…},"components":{…}}'>
  <section class="section" data-theme="dark">…HTML ya renderizado…</section>
</div>

Base.astro incluye un script mínimo. Si la página tiene al menos una isla, importa core/render/hydrate.tsx, que hace hydrateRoot sobre cada isla con los mismos props. Si no tiene ninguna, la página no carga React.

SEO incluido

  • Títulos y descripción: cada página tiene metaTitle, metaDescription, ogImage y noindex. Si están vacíos, usan los valores de Settings, y si tampoco hay ahí, los del código.
  • Etiquetas generadas: canonical absoluto, og:*, Twitter card, sitemap.xml, robots.txt y JSON-LD Organization en la home.
  • URLs: todas salen de pageHref() y resolveLink(). Los links internos son referencias a páginas, no paths escritos a mano. Agregar idiomas más adelante es cambiar esas dos funciones.

Producto

Remarkable Editor

Es la primera pestaña del Studio. Tiene tres columnas: páginas y capas, canvas y propiedades. Arriba están deshacer y rehacer, + Add, el selector de dispositivo, ▶ Play y Publish.

Qué se puede hacer

  • Texto en el lugar. Doble clic en headings, párrafos, eyebrows, botones, título y cuerpo de cards, Big Type y Scroll Text. El rich text tiene una barra flotante con negrita, itálica, link y quitar link.
  • Capas. Árbol con arrastre (antes, después o adentro), insertar, duplicar, borrar, mover, y copiar y pegar entre páginas.
  • Arrastre en el canvas. El bloque seleccionado muestra un agarre ⠿. Una línea azul indica dónde cae, y se valida con las mismas reglas que las capas.
  • Selección múltiple. Con ⇧ o ⌘ + clic en el canvas o en capas. Borrar, duplicar, copiar y mover aplican a todos.
  • Imágenes. Se arrastra un archivo sobre una imagen, card, parallax o fondo de sección, o se sube desde el panel.
  • Propiedades generadas del schema. Cada campo de cada bloque tiene su control; verify falla si alguno queda sin control.
  • ▶ Play. Reproduce las animaciones decorativas una vez. Mientras editás quedan quietas.

Cómo guarda

El editor usa el almacén de documentos del propio Studio, sin otro SDK. Los cambios se aplican al instante en local y se guardan como borrador. Publish publica el documento. Como el sitio es estático, publicar dispara un rebuild (ver Hosting y publicación).

Edición de texto sin saltos del cursor

Mientras escribís, el canvas retiene los renders que llegan del editor. Al terminar, restaura el DOM exacto que React espera y recién ahí aplica el valor nuevo. El rich text se convierte entre Portable Text y HTML editable en core/editor/richtext.ts, y mantiene los destinos de los links existentes por su clave.

Estilos y tokens

Todo el diseño sale de src/theme/tokens.css, el primer archivo que se toca en cada proyecto. Ahí están los colores por tema (light, dark, brand), los radios, la escala tipográfica, el espaciado y el ancho de página. Tailwind 4 los expone como utilities (bg-surface text-fg gap-md rounded-main), y como los colores leen el data-theme de la sección, cada bloque se adapta solo al tema. La paleta por defecto de Tailwind no está, a propósito: un color nuevo se agrega como token.

Panel de estilo

Cada bloque tiene un campo design que el editor muestra como panel de estilo. Hay solo tokens, no CSS libre, y se puede definir para todas las pantallas, tablet y mobile.

PropiedadValores
Margin, paddingnone xs sm md lg xl 2xl 3xl

core/style/stylesheet.ts convierte esos valores en una sola hoja de estilos por página, con un selector por bloque. Los valores del panel van con !important porque el panel es la autoridad final sobre ese bloque:

[data-b="9c2e"][data-b] { padding-top: var(--space-lg) !important; }
@media (max-width: 767px) {
  [data-b="9c2e"][data-b] { padding-top: var(--space-sm) !important; }
}

Box

Es el contenedor libre: apila, pone en fila o arma una grilla, con gaps de token, alineación y wrap. Se puede anidar. En tablet las grillas pasan a 2 columnas y en mobile a 1; las filas se apilan en mobile.

Producto

Componentes

Funcionan como los de Webflow. Un componente es un documento component con secciones. Una página lo usa con un bloque componentRef (una instancia). Si editás el componente, cambian todas sus instancias.

En el editor

  • Make component: guarda la sección seleccionada en la librería y la reemplaza por una instancia.
  • + Add: lista los componentes de la librería para insertarlos como instancia.
  • Edit component: abre el componente original para editarlo.
  • Detach: convierte la instancia en una copia suelta y editable.
  • El canvas selecciona una instancia como un solo bloque.

Overrides por instancia

Si hacés doble clic en un texto o soltás una imagen dentro de una instancia, el cambio se guarda solo en esa instancia, en su lista overrides. El original no se toca. Cada override apunta a "<claveDelBloque>.<campo>", se aplica al renderizar (core/render/overrides.ts) y el panel los lista con un botón Reset.

Límite actual

Los componentes son secciones enteras y solo viven en el primer nivel de una página. No se anidan ni se insertan adentro de otra sección. Ver Lo que sigue.

Producto

Motion

GSAP se importa en un solo lugar, core/motion/gsap.ts, que además define cuándo corre cada tipo de animación. La regla es distinguir el movimiento que hace falta para llegar al contenido del que es decorativo:

TipoEjemplosSitioCanvas del editorReduced motion
LayoutPin, scroll horizontal, sticky con scrub, parallaxCorreCorreAlternativa nativa
DecorativoSplits de texto, entradas, loop del marquee, revealsCorreQuieto · ▶ PlayNo corre

Reglas para bloques animados

  • useGSAP con scope, dentro del componente React. Nunca un <script> de Astro con querySelector: el editor re-renderiza bloques y el script no ve los nodos nuevos.
  • Si el bloque tiene hijos: dependencies: [claves] y revertOnUpdate: true, para que insertar o borrar reconstruya la animación.
  • Pinear un elemento interno, nunca el que lleva data-sanity-path. React es dueño del nodo exterior y el pin-spacer de GSAP va en el medio.
  • El texto se divide en un wrapper con key por texto. SplitReveal y useSplit ya lo hacen; reusarlos.
  • Lo que está en pantalla al cargar entra por tiempo, no por scrub, porque arrancaría a mitad de camino.
  • Declarar js en meta.ts. Si no, en el sitio público el bloque se ve pero no se mueve.

Proyecto nuevo

El arranque está empaquetado como una skill de Claude Code, remarkable-astro, que vive en skills/ del repo. Se instala una vez por máquina:

gh repo clone seba-seb/Remarkable-Astro /tmp/remarkable -- --depth 1
cp -R /tmp/remarkable/skills/remarkable-astro ~/.claude/skills/

Después alcanza con pedirle a Claude "un proyecto nuevo con Remarkable para <cliente>". La skill sigue estos pasos y frena en los que te tocan a vos:

  1. Datos mínimos

    Nombre, organización de Sanity del cliente, hosting y dominio, si existe.

  2. Repo

    Copia el starter, inicia git y corre npm install, que aplica patches/ y falla si Sanity no es 6.3.0.

  3. Sanity

    Crea el proyecto y el dataset production público, agrega http://localhost:4321 a CORS con credenciales y arma .env.

  4. Contenido demo Vos

    npx sanity login && npx sanity dataset import sanity/seed.ndjson production. Usa tu login, sin tokens.

  5. Primer arranque

    npm run dev: la home, /studio y el editor con la página.

  6. Hacerlo del cliente

    Tokens, tipografía, header y footer, bloques que sobran, bloques propios, Settings y Navigation.

  7. Roles Vos

    Invitar al cliente como editor o contributor.

  8. Hosting y publicación Vos

    Variables de entorno, CORS del dominio y el webhook de Sanity al deploy hook del host.

  9. Cierre

    npm run verify en verde y el smoke test logueado.

Tokens

El código

La regla que sostiene el starter: src/core es igual en todos los proyectos. Un arreglo en core va primero al starter y después se copia a los proyectos. Lo de cada cliente vive en theme, chrome y blocks. Cuando haya 3 o más proyectos en producción, core pasa a ser un paquete privado y los arreglos llegan con npm update.

src/core/ infraestructura · igual en todos los proyectos editor/ EditorTool, CanvasApp, FieldControls, ops, paths, protocol, richtext render/ PageBuilder, BlockRenderer, components (instancias), overrides, hydrate style/ tokens del panel, stylesheet por página, schema del campo design motion/ gsap.ts (política), ScrollRefresh, useSplit, SplitReveal sanity/ client + loadQuery, site loader, queries, editable(), env studio/ inputs propios del Studio (sliders, enums, responsive) lib/ routes (pageHref/resolveLink), clean, staleChunkReload, types src/blocks/ una carpeta por bloque · meta.ts = el registro src/theme/ tokens.css (lo primero que se cambia) + globals.css src/chrome/ header y footer del proyecto src/documents/ page, component, settings, navigation src/pages/ rutas · /edit-canvas = canvas · /lab/[slug] = banco de motion (solo dev) patches/ ajustes a sanity@6.3.0 (ver su README) scripts/ verify, check-editor-schema, seeds skills/ skill remarkable-astro para proyectos nuevos docs/ esta documentación CLAUDE.md reglas para trabajar en el código (fuente de verdad)

Reglas que más se rompen

  • Los bloques reciben todo por props y llevan {...editable(…)} en su raíz. Nunca hacen fetch: el canvas los dibuja con el documento que recibe.
  • Estilos con utilities de Tailwind sobre tokens. Sin colores literales.
  • Los assets de diseño (logos, texturas) son código, no van al CMS.
  • macOS no distingue mayúsculas: nunca Foo.tsx y foo.ts en la misma carpeta.

Agregar un bloque

  1. Schema y componente

    src/blocks/<tipo>/schema.ts con defineType y un ícono de @sanity/icons, más <Tipo>.tsx, que recibe { block, path, ctx }.

  2. Registro

    Entrada en meta.ts: título, slot si contiene otros bloques, margin, y js si corre algo en el navegador.

  3. Mapas

    Registrarlo en schemas.ts y components.tsx. El compilador marca error hasta que esté.

  4. Editor (opcional)

    Contenido al insertarlo en defaults.ts, texto editable en TEXT_TARGETS y soltar imagen en IMAGE_FIELDS (ambos en CanvasApp.tsx).

// src/blocks/meta.ts
quote: { title: "Quote", margin: true },
ticker: { title: "Ticker", js: true },
heading: { title: "Heading", js: (b) => !!b.animation && b.animation !== "none" },
// src/blocks/quote/Quote.tsx
export function Quote({ block, path, ctx }: BlockProps<QuoteData>) {
  return (
    <blockquote className="text-h-lg text-fg"
      {...editable(ctx.documentId, ctx.documentType, path, block._type)}>
      {block.text}
    </blockquote>
  );
}

Para borrar un bloque: su carpeta, su entrada en meta.ts, las dos entradas de los mapas y cualquier accepts que lo nombre. El compilador te lleva a cada una.

Calidad y pruebas

npm run verify

Corre antes de cada entrega y después de cualquier cambio en core. Revisa lo que se rompe sin avisar:

  • La versión de Sanity instalada tiene su parche.
  • Los links y las rutas resuelven bien (routes.check).
  • Cada campo de cada bloque tiene un control en el panel (check-editor-schema).
  • Insertar, mover, borrar y duplicar mantienen el documento válido, y la detección de islas es correcta (ops.check).
  • Los tokens generan el CSS esperado, sin inyección de selectores (stylesheet.check).
  • Los overrides se aplican al bloque correcto y nunca tocan el original (overrides.check).
  • El build pasa, el HTML público no tiene código del editor ni del Studio, y la home queda en 250 KB de JS o menos.
  • La home tiene contenido real, canonical absoluto, sitemap y robots.
  • Con una URL (npm run verify -- https://dominio), además responden /, /studio y /edit-canvas.

Banco de motion

/lab/<slug>, solo en dev, repite sobre el PageBuilder real lo que hace el editor. Escribe en cada texto, inserta y borra dentro de bandas pineadas, invierte y duplica secciones, cicla animaciones y temas, y hace 25 ediciones rápidas, la mitad scrolleado dentro de un pin. Después de cada paso verifica:

  • sin errores de React;
  • un pin-spacer por banda;
  • el recorrido del pin coincide con el del track;
  • sin ScrollTriggers colgados;
  • sin splits trabados;
  • sin overflow horizontal.

Las páginas de prueba son /lab-noir, /lab-kinetic y /lab-stack.

Smoke test logueado

Los flujos que necesitan login no se pueden automatizar sin credenciales. Se prueban a mano, en una página descartable, antes de entregar un sitio:

  1. Escribir en un heading sobre la página, recargar, y que el texto siga ahí.
  2. Negrita, itálica y link en un párrafo. Insertar, duplicar, borrar y arrastrar una capa. Deshacer y rehacer.
  3. Soltar una imagen sobre un bloque Image: se sube y aparece.
  4. Make component sobre una sección. Editar texto en una instancia: cambia solo esa. Reset. Edit component: cambian todas.
  5. Publish, después npm run build, y el cambio está en la página estática.
  6. Entrar con un usuario de rol cliente: no ve estilos ni acciones de estructura.

Contexto

Decisiones

Por qué está hecho así. Antes de cambiar alguna de estas, conviene leer el motivo.

Editor propio en vez de Sanity Presentation

Problema. Presentation era lento para editar: había que hacer clic en el overlay, buscar el campo en un formulario y esperar la ida y vuelta. No se podía escribir sobre la página y dependía de 7 parches.

Decisión. Reemplazar solo la UI de edición, con APIs públicas del Studio. Presentation, /preview, el draft mode y visual-editing se eliminaron.

Sanity como base de datos

Problema. Login, roles, borradores, historial, tiempo real e imágenes son meses de infraestructura.

Decisión. No construir eso: Sanity lo resuelve y el Studio sigue disponible para settings, menús y colecciones.

Canvas en iframe, sin datos propios

Problema. El CSS del sitio y el del Studio no pueden mezclarse, y una ruta del canvas con datos expondría borradores.

Decisión. Un iframe del mismo origen que solo dibuja lo que le manda el editor autenticado. Además da breakpoints reales.

Sitio estático con islas por sección

Problema. Hidratar toda la página costaba 138 KB de JS aunque casi nada se moviera.

Decisión. Sin Presentation ya no hace falta hidratar todo: HTML puro y React solo en las secciones con js.

Sanity fijo en 6.3.0

Problema. patches/ ajusta formularios del Studio y solo encaja en una versión exacta.

Decisión. Fijar la versión y hacer que install y verify fallen si se desvía. Actualizar es un trabajo planificado.

Estilos solo con tokens

Problema. El CSS libre y el posicionamiento absoluto equivalen a construir Webflow entero, y rompen la consistencia de la marca.

Decisión. El panel solo ofrece tokens. Los bloques nuevos se escriben en código y el editor compone y estila con ellos.

Core aislado, plantilla primero

Problema. Un paquete privado desde el día uno agrega versionado antes de saber qué cambia por proyecto.

Decisión. Copiar el starter y mantener src/core intacto. Extraerlo a paquete cuando haya 3 o más sitios en producción.

Sin i18n, pero preparado

Problema. Ningún proyecto actual lo pide.

Decisión. Todas las URLs pasan por pageHref() y resolveLink(). Agregar idiomas se hace en un solo lugar.
